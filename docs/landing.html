§ 01 · Origin

I kept generating structured docs and throwing them away.

I kept asking AI tools to generate structured documents. ERD visualizations, changelog tables, postmortem writeups. Each time I'd look at the output in a browser, get what I needed, and discard the file.

But the output was already organized. The tables had the data. The section headers mapped the architecture. The only waste was starting from zero every time.

So I stopped starting from zero. I made a template with section markers so I could update what changed and leave everything else intact. The file compounds over time instead of getting thrown away.

I've been using it to stay oriented while building Tanso, and it's been useful enough to share.

§ 02 · Where it fits

It doesn't replace your other docs. It sits underneath them.

Every project accumulates doc files. Each one serves a different audience. human-docs is the layer the others assume but never provide — the filtered, structured view that keeps the builder oriented without reading the full codebase, git log, or agent context.

File Who reads it What it does
README.md Someone evaluating the project on GitHub First impression. Setup instructions.
CLAUDE.md / .cursorrules AI coding agents Machine-readable instructions. Tells the agent how to behave.
llms.txt AI agents fetching context Machine-readable site/project context.
OpenAPI spec Integrators building against your API Formal contract. Every parameter, every response shape.
human-docs The builder. The person who needs to keep up. Human-readable view of the system — what it looks like, what shipped, what broke. AI agents maintain it. Humans read it.
§ 03 · How it works

Three ways to keep it current — from manual to automatic.

The doc is just an HTML file with <!-- SECTION:name --> markers. Any AI tool that reads files can update one section without touching the rest. Pick the level of automation that fits your workflow.

1

Tell the agent what changed.

Lowest friction. You know what you just shipped — just describe it.

> "Update the changelog
and postmortems sections.
Here's the diff: [paste]"

// Agent finds the SECTION
// markers, edits between
// them, leaves the rest.
human in the loop · review before commit
2

Run update-doc.sh

The script diffs git history, maps changed files to doc sections, and prints a prompt to paste into your AI tool.

# changes since last update
./update-doc.sh

# changes in last 5 commits
./update-doc.sh HEAD~5
git-aware · semi-automatic · review the prompt
3

Hook it into your workflow.

Wire update-doc.sh into a git hook or CI step. Script outputs which sections are stale; your agent handles the rest.

# .git/hooks/post-commit
#!/usr/bin/env bash
./update-doc.sh | \
  claude --commit
fully automatic · every update is a git commit you can diff

The tradeoff: options 1 and 2 keep the human in the loop (AI generates, humans curate). Option 3 is fully automatic — faster, but you give up the review step. Every update is still a git commit, so you can always diff what changed.

§ 04 · The marker pattern

Surgical updates, not regeneration.

Each section of the template is wrapped in HTML comments. Agents edit content between them — never touching the rest of the file. Like reviewing a git diff: only what actually changed.

<!-- SECTION:changelog -->
<h2 id="changelog">Changelog</h2>
<table id="changelog-table">
  <tr data-type="feature">
    <td>FEATURE</td>
    <td>2026-05-12</td>
    <td>Added pgvector to search</td>
  </tr>
  <!-- agent adds new rows here -->
</table>
<!-- /SECTION:changelog -->

Section mapping does the heavy lifting: a schema migration updates data-model + entity cards. A new endpoint updates api + changelog. A bug fix updates changelog + postmortems. The doc stays coherent because the markers say what's where.

§ 05 · Sections

Six PM-minded sections, out of the box.

Not just endpoint lists. The default template asks the questions a builder actually needs to answer when they sit down — definitions that prevent overloaded-term bugs, postmortems that prevent repeating them.

SECTION:definitions

Definitions

"What does X mean in this codebase?"

Prevents the #1 source of bugs: overloaded terms. Pulls from database columns, API fields, and comments where something is clarified.

SECTION:data-model

Data Model

"What tables exist and how do they relate?"

Mermaid ERD plus entity cards, grouped by domain (core, billing, analytics). Generated from migrations, schema files, or ORM models.

SECTION:pages

Pages & Routes

"What can users see?"

Every user-facing route with its path, component name, and purpose. Read from the router config or file-based routing structure.

SECTION:api

API Surface

"What can code call?"

Endpoints grouped by domain. Method, path, purpose. Read from route/controller definitions.

SECTION:changelog

Changelog

"What shipped?"

Filterable by type (bug, feature, perf, docs). Generated from git log, with bug entries linked to postmortems by ID.

SECTION:postmortems

Postmortems

"What broke and how do we prevent it?"

Root cause, impact, fix, prevention rule. Numbered PM-1, PM-2, etc. The most valuable section — changelogs record what happened, postmortems record what not to do again.

Optional sections defined in PROMPT.md: User Stories (acceptance criteria), Customer Model (multi-tenant products), Board (kanban for small teams), Emails (transactional catalog).

§ 06 · Philosophy

Four opinions baked in.

Docs should be readable without context.

Hand this file to someone who just joined your team. They should understand what the product does, what the data looks like, what broke recently, and what shipped — without reading any other file.

Postmortems are the most valuable section.

Changelogs record what happened. Postmortems record what not to do again. Root cause, impact, fix, and a prevention rule. Numbered, linked from changelog bugs, surfaced for every new contributor.

One file is a feature, not a limitation.

The moment you split docs across files, someone stops updating one of them. One file means one place to look, one thing to update, one artifact to share.

AI generates, humans curate.

The AI reads your codebase and fills in the template. You read the output and fix what it got wrong. Over time the doc compounds — each update adds to the changelog, each bug adds a postmortem, each migration updates the ERD.

First time

Copy the template

Drop template.html into your project — wherever makes sense.

# suggested:
cp template.html docs/architecture.html
Step 02
Paste the prompt

Open your AI tool (Claude Code, Cursor, Codex). Paste PROMPT.md. Point it at your codebase.

# or pipe it in:
cat PROMPT.md | claude
Step 03
Open in browser

The AI fills in the sections. You read the output, fix anything wrong, commit the file. That's it.

# works in every browser
open docs/architecture.html
