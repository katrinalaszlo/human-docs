Cal.com Architecture

Open-source scheduling infrastructure. Prisma + tRPC + Next.js monorepo. Updated 2026-04-25.

Definitions

Terms that have precise meanings in Cal.com. Mixing them up causes scheduling bugs.

Scheduling Types (team events)

ROUND_ROBIN

Rotates between available hosts. Each host has priority and weight fields. Higher priority hosts are preferred; weight controls distribution ratio among same-priority hosts.

COLLECTIVE

All hosts must be available. The booking is only created when every assigned host's calendar is free. Used for panel interviews, group calls.

MANAGED

Team-level event type that syncs configuration to all members. Admin controls the template; members get individual copies they can't fully override.

Booking Lifecycle

1. Slot check
  GET /api/trpc/viewer.slots.getSchedule
  → reads Schedule + Availability rows, checks calendar busy times via Credential
  → returns available slots in booker's timezone

2. Booking created
  POST /api/trpc/viewer.bookings.create
  → status = ACCEPTED (or PENDING if requiresConfirmation = true)
  → Attendee rows created, calendar events pushed via credentials
  → Webhook fired: BOOKING_CREATED

3. Confirmation (if required)
  Host confirms → status = ACCEPTED, calendar events created
  Host rejects → status = REJECTED, attendee notified

4. Reschedule
  Original booking status → CANCELLED (with rescheduledReason)
  New booking created with link to original

5. Cancellation
  status → CANCELLED, calendar events deleted
  Webhook fired: BOOKING_CANCELLED

Postmortems

Root cause analysis for scheduling edge cases.

PM-1: Round-robin skipped hosts with equal priority
FieldDetail
Root CauseRound-robin selection sorted hosts by priority and picked the first. When multiple hosts had the same priority, only the first (by ID) was ever selected. The weight field didn't exist yet — distribution was effectively first-wins.
ImpactTeams with 5 equal-priority hosts saw one host getting all bookings. Others got none.
FixAdded weight column to Host. Selection now uses weighted random among same-priority hosts. Default weight = 100 for backward compatibility.
PreventionAny "pick one from a group" algorithm needs a distribution mechanism, not just ordering. Test with N > 2 same-priority hosts.
PM-2: Timezone offset double-applied on reschedule
FieldDetail
Root CauseReschedule flow reads the original booking's startTime (stored as UTC), converts to the booker's timezone for display, then converts back to UTC on submit. The second conversion applied the offset again because the intermediate value was already adjusted.
ImpactRescheduled bookings in UTC+5 shifted by 10 hours instead of 5. Users in UTC+0 were unaffected (offset = 0).
FixReschedule form now receives raw UTC time and only converts once for display. Submission sends the selected slot's UTC time directly — no round-trip conversion.
PreventionStore and transmit times in UTC. Convert only at the display boundary, never in intermediate processing. Test reschedule in UTC+N where N > 0.
PM-3: Collective booking ignored DST transition
FieldDetail
Root CauseSlot computation cached timezone offsets at query time. When a collective event spanned a DST boundary (e.g., booking for Monday after clocks change on Sunday), one host's offset was stale. The slot appeared free because the cached offset put the busy period in the wrong hour.
ImpactDouble-booking for collective events near DST transitions. One host had a conflict that the slot calculator didn't see.
FixSlot computation now resolves timezone offset per-slot, not per-query. Uses the target date's offset (via Intl.DateTimeFormat) instead of "today's" offset.
PreventionNever cache timezone offsets across dates. DST transitions happen mid-range. Test availability queries that span the next DST boundary in the host's timezone.
